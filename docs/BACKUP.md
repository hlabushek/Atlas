# Резервное копирование и восстановление
PostgreSQL: `pg_dump -Fc`, stdout записывается как бинарный поток, не PowerShell text redirect. Не копируйте работающий volume как файл. Скрипт `python scripts/check_restore.py` сохраняет dump в игнорируемой `.backups`, создаёт БД `atlas_restore_drill_<random>`, выполняет pg_restore, сравнивает число/MD5 содержимого всех таблиц и migration version, затем удаляет **только созданную им** временную БД. Рабочая БД не заменяется. Отчёт содержит только число таблиц/версию/имя backup.
Для точного сравнения остановите API/worker/scheduler/telegram на время drill; PostgreSQL и Redis остаются запущены. Если параллельная запись изменила исходную БД, script откажется объявлять PASS. Dump сам по себе transactionally consistent; сравнение с текущей рабочей БД требует отсутствия писателей. Перед переключением production сначала отдельно восстановите БД, проверьте чтение и настройки, затем согласуйте downtime/переключение. Автоматического переключения нет.
29 сентября 2026 проведены настоящие dump/restore drills до и после миграции этапов 6/7; содержимое совпало, исходная БД не изменилась. Backup полного SQL состояния включает задачи/approvals/вложения/embeddings/subscription capabilities, поэтому приватен. Храните вне Git, с OS ACL/шифрованием и независимой защищённой копией; расписание/retention/внешнее хранилище ещё не настроены.
SQLite: используйте штатный sqlite3.Connection.backup() для согласованной копии, либо остановите писателей и скопируйте atlas.db. Перед 0008 сохранены binary backups в .backups. JSON export — только перенос разговоров/памяти, не полный backup задач.
Секреты `.env`, VAPID/Companion TLS keys и external sessions резервируйте отдельно с ограниченным доступом. Dump не восстанавливает сертификаты, environment или внешние данные. Redis здесь не источник истины очереди; durable задачи/checkpoints хранятся в SQL.

## Production VPS Atlas (30 сентября 2026)
`ops/backup/atlas-backup.sh` создаёт daily `pg_dump -Fc`, сразу шифрует AES-256 с отдельным случайным ключом вне репозитория, проверяет расшифровку/архив и хранит 30 дней в `/opt/atlas/backups/encrypted` (каталог и файлы доступны только root). Systemd запускает backup ежедневно в 03:30 MSK. Еженедельный restore drill восстанавливает последний архив во временную отдельную БД, проверяет Alembic revision и число таблиц, затем удаляет только созданную БД. Он не останавливает работающие сервисы.

Ключ находится в `/etc/atlas-backup/passphrase`, режим 0600. Он не попадает в Git, логи или базу. Первый production dump успешно создан 30 сентября 2026 года; немедленный restore drill PASS: Alembic revision 0011, 35 таблиц, временная БД удалена. Ежедневный и еженедельный systemd timers включены. Локальные зашифрованные копии на том же VPS не защищают от потери/компрометации VPS; для disaster recovery добавьте отдельное offsite-хранилище и сохраните копию ключа независимо с доступом только владельца. Исторические migration dumps в `/opt/atlas/backups` и `/opt/atlas/staging` не удаляются этой ротацией.

Копия первого зашифрованного архива и ключа восстановления перенесена с проверкой SHA-256 в `%LOCALAPPDATA%\Atlas\Backups` на Windows, с ACL только для владельца и SYSTEM. Скрипт `ops/backup/sync-encrypted-to-windows.ps1` повторяет копирование при входе пользователя; задача Планировщика дополнительно назначена на 05:00, но её исполнение на этой машине после следующего входа надо проверить. При выключенном ПК offsite-копия отстаёт до его следующего запуска. Не храните единственную копию ключа на VPS.
